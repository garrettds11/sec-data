# Detection and response fixture

The story bundle emits versioned `detection-rules.jsonl`, `detection-decisions.jsonl`, `alerts.jsonl`, `case-actions.jsonl`, and `response-firewall.jsonl`. These are synthetic, project-owned records. `response-truth.json` holds expected outcomes and cross-source references and should remain outside analyst-facing indexes. They are not Splunk Enterprise Security notables or records from a commercial ticket system.

Two rules use observations and inventory available to a detector:

1. `recon-port-burst` alerts after three observed network probes from the external scanner. The same candidate from the inventoried approved scanner is suppressed, with a recorded reason. This is a probe signal, not an incident conclusion.
2. `sensitive-read-outbound` correlates a Windows 4663 read of a confidential catalog path with a later Zeek HTTP POST. The Windows logon ID supplies the user's source host; the rule requires that source IP, an unauthorized destination from the entity catalog, matching byte size, and a one-minute window. The rule uses source records and catalogs. The separate answer key is consulted only after the alert is derived.

Each alert includes the rule version, evidence references, observation and availability times, firing time, detection latency, and severity. Recon evidence uses its `collected_at`; this fixture assumes a two-second availability lag for Windows file events and one second for Zeek HTTP. These are model assumptions, not measured ingestion latency. The validator recomputes alerts and decisions from the source records and rejects evidence that becomes available after firing.

The case opens on the read/outbound alert, records a hypothesis, then records an analyst review. The review cites the public exposure, edge request, failed web login, later operator Windows logon, and endpoint registry activity as context. It explicitly leaves actor continuity between the public probe and the operator unproven. The confirmed conclusion is an outbound policy violation; the uploaded content remains unverified by the sensors. The case applies a destination block for the bastion. A later retry to that same endpoint is blocked with zero payload and no Zeek HTTP/connection event. The pre-existing remediation records change a vulnerability and a control state, and the later assessment shows their revised status. The final case action closes after that assessment.

## Splunk smoke test

[Splunk's Alerts data model](https://docs.splunk.com/Documentation/CIM/6.1.0/User/Alerts) describes higher-level events from alerting systems and explicitly distinguishes them from Splunk alerts and notable events. [Change](https://docs.splunk.com/Documentation/CIM/6.1.0/User/Change) is a candidate for containment and remediation state changes. [Ticket Management](https://docs.splunk.com/Documentation/CIM/6.1.0/User/TicketManagement) is a candidate for case state transitions. No vendor app is claimed for these project-owned sources, and no ES feature is assumed.

In a test Splunk instance, ingest the project-owned JSONL under separate custom sourcetypes and set `_time` from `fired_at`, `time`, or `evaluated_at` as appropriate. Inspect parsed `alert_id`, `rule_id`, `severity`, case ID/state, target, action, and change IDs. Add explicit field aliases, tags, and event types only where they fit the relevant CIM dataset, then verify data model inclusion in Splunk. Run searches for the scan alert, suppressed approved scanner decision, read/outbound alert evidence, case chronology, allowed-before/blocked-after destination pair, and follow-up findings. The pinned Windows and Zeek add-ons from [data access](data-access.md) remain candidates for the underlying evidence. **No live ingestion, CIM inclusion, or Enterprise Security integration has been verified.**
